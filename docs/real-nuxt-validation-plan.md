# 真实 Nuxt 应用验证方案

日期：2026-09-28。状态：已按后续要求改为 monorepo，并完成应用基础与核心验收。本文保留完整目标，尚未完成的场景不计入通过结果。当前已建立两个真实 Nuxt 应用、六组生产构建和 18 项核心 E2E，执行结果见 [验证记录](validation.md)。

## 1. 目标与完成定义

建立可重复运行的 Nuxt 3／4 生产应用验收，覆盖「业务数据 → Nuxt SSR／预渲染 → 实际 HTML 与 payload → 扩展采集 → 侧边栏展示与导出」。

完成后，兼容结论应能回答：使用哪个 Nuxt 版本、哪种构建配置、哪些页面场景，在什么浏览器和 Node 环境下验证通过。测试输出应足够定位问题发生在应用生成、资源读取、扩展解析还是界面展示。

本轮围绕当前产品范围：读取 Nuxt 3／4 的初始 JSON payload，Nuxt 2 按此前要求排除。运行时状态模式、快照对比、Firefox、多 iframe 属于独立功能方向；扩展保持不执行目标网站自定义 reviver 的现有约定。

## 3. 版本与依赖策略

2026-09-28 已通过 npm registry 查询版本及运行要求：

| 项目       | 选定基线                        | 策略                                               |
| ---------- | ------------------------------- | -------------------------------------------------- |
| Node       | 22.23.3                         | 沿用根目录 `.nvmrc`，所有脚本先加载 nvm 并切换版本 |
| pnpm       | 10.19.0                         | 沿用现有 packageManager                            |
| Nuxt 3     | 3.21.11                         | 测试应用精确锁定，不使用浮动 `3.x`                 |
| Nuxt 4     | 4.5.2                           | 测试应用精确锁定，不使用浮动 `latest`              |
| 扩展解析器 | devalue 6.0.2                   | 沿用现有版本                                       |
| 测试框架   | Vitest 5.0.2、Playwright 1.63.0 | 复用现有依赖和浏览器测试能力                       |

Nuxt 3.21.11 的 Node 约束为 `^20.19.0 || >=22.12.0`，Nuxt 4.5.2 为 `^22.19.0 || ^24.11.0 || >=26.0.0`。当前 Node 22.23.3 已满足两者；monorepo 实施时最低约束提高到 `^22.19.0`，后续依赖升级因 lint-staged 要求进一步提高到 `^22.22.1`；`.nvmrc` 保持不变。[Nuxt 3 包元数据](https://registry.npmjs.org/nuxt/3.21.11)、[Nuxt 4 包元数据](https://registry.npmjs.org/nuxt/4.5.2)

按后续指令采用 pnpm workspace：扩展、Nuxt 3、Nuxt 4 分别位于 `apps/extension`、`apps/nuxt3`、`apps/nuxt4`。每个应用有独立 package.json，共用根目录 pnpm-lock.yaml，在根目录一次安装。`resolvePeersFromWorkspaceRoot: false` 避免用根工具链隐式满足应用的 peer 依赖；Nuxt、Vue、Nitro、Vite 和 devalue 按各自应用的依赖图解析，不通过 overrides 强制共用扩展版本。实际解析版本记录在验收报告。

安装前再次查询最新版本；如果与本方案不同，先评估变更并更新明确的版本基线。日常测试只按锁文件安装。新增依赖限于构建应用所需的 Nuxt／Vue 及其配套工具，首轮复用已有 Playwright，不额外引入 Nuxt 测试框架。

## 4. 必测构建矩阵

每个 Nuxt 大版本运行三种配置，共六组生产构建。各组使用独立输出目录，避免后一个构建覆盖前一组服务使用的文件。

| 配置       | Nuxt 3 | Nuxt 4 | 部署与关键设置                                                             | 核心验证                                       |
| ---------- | ------ | ------ | -------------------------------------------------------------------------- | ---------------------------------------------- |
| 动态 SSR   | 必测   | 必测   | 生产构建 + Node 服务；根路径；JSON payload；提取关闭                       | 内嵌数据、真实接口、状态、错误、导航、CSR 路由 |
| 内嵌预渲染 | 必测   | 必测   | generate 后静态托管；根路径；`payloadExtraction: false`                    | 构建产物内嵌数据可读，直接访问和刷新正确       |
| 外部预渲染 | 必测   | 必测   | generate 后静态托管；`app.baseURL: '/inspect/'`；`payloadExtraction: true` | 真实外部文件、内外合并、嵌套路由、子路径与导出 |

配置显式声明 `renderJsonPayloads: true` 和 payload 提取策略。Nuxt 3 保留其默认版本行为，Nuxt 4 保留其默认版本行为；不为追求相同结果而把 Nuxt 3 切换到 Nuxt 4 兼容模式。

Nuxt 4.5.2 还支持 `payloadExtraction: 'client'`，初始数据内嵌、导航数据单独提取；选定 Nuxt 3 的配置仅支持布尔值。该模式列入扩展矩阵，不误用到 Nuxt 3。[Nuxt 3 配置源码](https://github.com/nuxt/nuxt/blob/v3.21.11/packages/schema/src/config/experimental.ts)、[Nuxt 4 配置源码](https://github.com/nuxt/nuxt/blob/v4.5.2/packages/schema/src/config/experimental.ts)

首轮浏览器验收使用当前 Playwright 配套 Chromium。Chrome／Edge 正式版的手动冒烟另记浏览器版本及结果，不能由 Chromium 通过直接推导；目前官方建议使用 Playwright 自带 Chromium 进行扩展旁加载测试。[Playwright 扩展测试说明](https://playwright.dev/docs/chrome-extensions)

## 5. 测试应用设计

建立两个最小应用，保留各版本正常目录约定：Nuxt 3 的 pages／plugins 位于应用根目录，Nuxt 4 的页面与插件位于 app 目录。页面数量和数据规模保持小且可读。

共用文件只包含业务常量、场景描述和人工定义的预期结果，不从扩展解析器导入代码。包含 Vue 对象的样例由各应用使用自己的 Vue 实例创建，避免跨版本实例混用。

| 路由／场景             | 数据来源                                             | 验收意图                                                    |
| ---------------------- | ---------------------------------------------------- | ----------------------------------------------------------- |
| `/basic`               | 有显式键的 useAsyncData；useFetch 调用本地 Nitro API | 普通数据、数组、中文、空对象与空集合可读                    |
| `/types`               | useAsyncData 的服务端处理函数直接构造特殊类型        | Date、Map、Set、BigInt、RegExp、特殊数值、循环与共享引用    |
| `/state`               | useState 初始化固定值，页面按钮修改客户端状态        | 识别服务端初值，明确插件仍展示初始快照                      |
| `/errors`              | 受控的 useAsyncData 失败                             | 错误分类与状态码、错误信息；页面保持可操作                  |
| `/custom`              | 正常 Nuxt payload 插件注册示例 Money 类型            | 网站正常还原自定义类型；扩展显示未知类型标记、字段及诊断    |
| `/route-a`、`/route-b` | 两份不同业务标记，通过 NuxtLink 跳转                 | 真正的 SPA 导航、返回与整页刷新，正确区分初始文档与当前地址 |
| `/empty`               | 业务 payload 为空                                    | 与非 Nuxt 页面、采集失败明确区分                            |
| `/csr`                 | 动态服务的 routeRules 设置该路由 `ssr: false`        | 不误标成 SSR，不要求插件提供客户端后来获取的数据            |
| `/large`               | 确定性生成约 15,000 条记录及一个小 state 字段        | 展示预算、分类独立性、大原文导出及交互仍可用                |

特殊类型直接通过服务端数据处理函数生成；普通 HTTP JSON 接口用于验证 useFetch。二者分开，避免把 HTTP JSON 已丢失的类型误认为扩展解析失败。

静态配置只预渲染适用的明确路由，不把故意失败的服务器接口、CSR 路由或需要常驻 API 的页面列入生成清单。预渲染应用在构建阶段准备数据，静态托管阶段不依赖 Nitro API。

固定样例日期、业务 ID、数值和文本；框架生成的 buildId、采集时间等动态字段按规则校验，不比较整份 payload 的字节快照来判断业务兼容性。

## 7. 避免测试自证正确

预期结果分三层建立：

1. 人工定义业务预期，例如商品 ID、计数初值、Date 的 ISO 值、集合成员、预期引用关系。测试预期不调用生产 parsePayload 或 buildTree 生成。
2. 独立检查真实产物和页面，例如 HTML 中存在 payload 节点、外部文件及其摘要、页面水合后的业务展示。验证应用本身正确生成数据。
3. 从实际侧边栏与下载文件取得结果，核对业务语义、类型、来源和原文。数据收集必须走生产扩展流程。

Nuxt 应用不得自行拼装 `__NUXT_DATA__` 节点或直接把预先写好的 payload 传给扩展；所有正常场景数据必须经过 Nuxt 的序列化链路。测试专用就绪标记只描述页面挂载状态，不向扩展提供业务数据。

复杂对象展示检查使用字段路径与显式类型，不依赖 devalue 数据表索引、Vue 自动生成键或两个 Nuxt 版本恰好相同的响应式包装。

## 8. 测试设施与隔离

沿用持久 Chromium 上下文加载生产扩展，通过真实用户手势打开浏览器侧边栏，并继续使用 CDP 连接实际侧边栏目标。

已将通用夹具中的起始页面与侧栏就绪文本改为测试参数，剪贴板授权使用目标页面来源；原来的 `/inline`、端口 4318 和 `ShallowReactive` 保留为协议测试默认值。通用夹具只负责浏览器、扩展、侧边栏和清理，各场景负责自己的业务断言。

可给扩展的状态区、分类按钮和树节点补充少量稳定的测试定位属性，减少对 CSS 顺序及 `nth-child` 的依赖；保持数据采集和解析路径不变。

| 部分     | 设计                                                                                                                    |
| -------- | ----------------------------------------------------------------------------------------------------------------------- |
| 启动     | 先构建，再启动对应生产 SSR 或静态服务；使用项目编排脚本管理进程                                                         |
| 端口     | 仅监听 127.0.0.1；采用固定测试端口（协议 4318，真实应用 4430—4432／4440—4442）；占用时明确失败，不复用未知服务          |
| 就绪     | HTTP 健康检查、应用标识和浏览器挂载标记分别检查；禁止用固定 sleep 判定完成                                              |
| 静态托管 | 将产物根挂载到配置的 baseURL，按实际文件提供 HTML／JSON／JS；缺失 payload 返回 404，不能被 SPA fallback 伪装为成功 HTML |
| 构建     | 六组构建产物分别归档；同一应用的构建串行，避免 .nuxt 临时目录竞争                                                       |
| 浏览器   | 每项测试独立配置和扩展存储；全套先采用单 worker，避免侧栏焦点与下载目录竞争                                             |
| 清理     | 成功、失败和中断均关闭浏览器及本次启动的进程；不结束用户已有服务                                                        |
| 调试     | 记录最终 URL、页面标题、原始节点属性、后台和侧栏错误、下载文件及关键截图                                                |

外部故障由本地测试服务对真实构建文件施加。正常产物先通过基线检查；页面成功加载后，再通过本地控制入口开启故障并点击扩展刷新，避免将应用初次加载失败混入扩展降级断言。

慢请求采用可控的「开始／释放／完成」信号；先确认旧请求确实开始，再切换标签页，最后释放旧响应并再次断言。扩展后台请求不保证受页面级网络拦截控制，因此故障注入放在实际资源服务端。

根 TypeScript 配置已改为不收集源码；三个应用分别维护自己的配置与生成声明，根 `pnpm typecheck` 顺序检查各应用。ESLint 检查整个仓库源码，忽略 `.nuxt`、`.wxt`、`.output` 和测试产物。WXT 与 Tailwind 从扩展目录执行，扫描范围与 Nuxt 应用隔离。

## 10. 已实现命令与执行流程

| 命令                                                      | 行为                                                 |
| --------------------------------------------------------- | ---------------------------------------------------- |
| `pnpm install --frozen-lockfile`                          | 在根目录一次安装所有应用并准备类型                   |
| `pnpm typecheck`                                          | 分别检查扩展与两个 Nuxt 应用                         |
| `pnpm fixtures:typecheck`                                 | 仅检查两个 Nuxt 应用                                 |
| `pnpm fixtures:build`                                     | 构建六组配置，各自产物记录版本与根锁文件摘要         |
| `pnpm fixtures:build --major 4 --profile static-external` | 只重建指定版本和配置                                 |
| `pnpm test:e2e:nuxt`                                      | 构建扩展和六组应用、启动服务、执行真实应用 E2E、清理 |
| `pnpm test:e2e:all`                                       | 构建后顺序运行协议 E2E 和真实 Nuxt E2E               |

`pnpm test` 和 `pnpm test:e2e` 保持快速验证用途。已构建全部产物后，可用 `pnpm --filter @page-inspector/extension test:e2e:nuxt --project=nuxt4-ssr` 筛选配置，用 Playwright 的 `--grep` 筛选用例。当前配置会启动全部六个服务，按筛选结果只启动相关服务是后续优化项。

标准流程：加载 nvm → `nvm use` → 根目录冻结安装 → lint 与类型检查 → 单元测试 → 生产构建 → 已授权的真实侧栏 E2E → 记录兼容矩阵。服务启动不隐式下载依赖；关闭自动重试，失败原因按实际情况报告。

构建清单目前记录应用、Nuxt 版本、配置、Node 版本与根锁文件摘要；完整依赖版本另见验证记录。自动采集完整环境、所有原文摘要、失败截图与 CDP 日志仍属于后续报告增强项。

## 11. 结果与验收标准

报告至少包含：Node／pnpm／浏览器版本、应用 Nuxt／Vue／Nitro／devalue 实际版本、扩展构建摘要、应用配置、各场景状态、失败原因和产物路径。

失败时保留应用及扩展日志、最终来源信息、侧栏截图、相关原文和下载结果。Playwright trace 可作为辅助；当前侧栏通过 CDP 操作，trace 不一定完整记录其行为，因此必须另存 CDP 操作日志与侧栏截图。

完整验证方案最终应满足以下条件（当前核心验收不代表以下全部完成）：

- 六组核心配置全部完成生产构建与适用场景验收，报告中无隐藏跳过。
- 原有 48 项测试和 5 项协议 E2E 继续通过；新的真实应用类型检查、lint 和构建通过。
- 正常场景无未处理的页面／后台／侧栏异常，无非预期水合错误；故障用例只容许明确匹配的预期错误。
- 外部场景必须证明读取了真实外部数据，不能凭出现某个公共字段判定成功。
- 初始快照、SPA 当前地址、整页刷新后的新文档归属正确。
- 原文导出与采集来源文本一致；类型化视图与人工业务预期一致。
- 大数据达到预算时提示清晰，分类切换和原文导出仍能操作；耗时作为实测记录，不先写缺乏依据的性能保证。
- README 的兼容描述升级为明确的「版本 × 配置 × 场景」结果，旧协议样本验证与真实应用验证分别记录。

如果发现真实兼容缺陷，先判断是夹具设计、框架行为差异还是扩展问题，再补最小回归并修复。当前承诺范围内的缺陷必须解决；新发现的范围外能力应明确列为限制，不能通过删除断言或扩大通配条件使验收通过。

## 12. 后续扩展矩阵

核心六组通过后，按使用需求增加以下独立场景，分别统计结果：

| 场景                          | 增加的证据                                     | 额外边界                                                        |
| ----------------------------- | ---------------------------------------------- | --------------------------------------------------------------- |
| Nuxt 4 的 `'client'` 提取模式 | 初始内嵌与导航外部资源共存时快照归属正确       | 专属版本配置，不能套用 Nuxt 3                                   |
| 本地双来源模拟 CDN            | 实际生产 cdnURL 下的外部路径、跨来源读取和记录 | 浏览器读取资源也需满足相应 CORS；部署产物保持真实生成           |
| 带测试 Cookie 的资源          | 同源读取与跨域省略凭证符合扩展策略             | 使用合成身份；浏览器 SameSite 等策略影响要如实报告              |
| ISR／SWR 缓存路由             | 不同版本的 HTML 与外部 payload 被区分记录      | 必须按版本确认框架是否生成外部 JSON；不把两次读取误称为原子快照 |
| 真正的多应用页面              | 应用标识、来源选择与数据隔离                   | 先验证官方支持的部署方式；现有拼节点样例继续归类协议测试        |
| 流式 SSR／延后到达的数据      | 页面尚未完整加载时的读取与有界重试             | 只对支持并启用该模式的固定版本建立场景                          |
| Chrome／Edge 正式版           | 人工安装、打开侧栏与核心读取流程               | 独立记录实际浏览器版本与操作系统                                |

CDN、缓存、实验特性和多应用不纳入首轮六组的全部组合，避免矩阵无控制膨胀；首轮结果也不宣称已覆盖这些部署。
